# Legal & Data Sourcing Notes

**Last updated:** 2026-08-02
**Status:** Living document — update whenever a new data source or
dependency is added to the project.

**Not legal advice.** This document is a working record for the
researcher's own reference and for transparency to reviewers/collaborators,
not a substitute for qualified legal counsel. As an independent researcher
without an institutional export-control office, the researcher bears full
responsibility for staying within safe categories — this doc exists to make
that easy to verify at a glance.

## 1. Principle

This project needs zero real operational spacecraft data, real signing
infrastructure, or export-controlled technical data to support its actual
research claims (supply-chain assurance comparison). Everything is built
on open-source software, public-domain data, open standards, and synthetic
data generated by the project itself. This section exists to keep that
true — any proposed new dependency or data source should be checked against
the categories below before use.

## 3a. cFS source-handling policy

Convention adopted from adjacent projects in this workspace
(`mission-aware-satellite-cyber-recovery`) that follow the same pattern for
good reason — it keeps license provenance unambiguous and avoids ever
having a stale/modified copy of NASA source drift silently out of sync
with upstream:

- **Never vendor (copy/paste) NASA NOS3 or cFS source directly into this
  repository.**
- Reference upstream via a pinned commit checkout or git submodule only,
  preserving the original LICENSE and NOTICE files as distributed upstream.
- Any local modifications to cFS source for experimental purposes (e.g.,
  instrumenting an app for the onboard verification agent) must live as a
  clearly labeled patch/diff on top of the pinned checkout, not as an
  in-place edit that obscures what changed from upstream.
- Record the exact pinned commit/tag in `Technical-Design-Document.md` once
  Phase 1 selects a target cFS sample app.

## 3. Explicit exclusions

The following categories are **not used** in this project, by design:

- Real operational satellite/spacecraft flight software from any defense
  contractor or classified program.
- Real signing keys, HSM infrastructure, or credentials from any
  operational mission.
- Any dataset requiring an export license (ITAR/EAR) to access or use.
- Any real mission's detailed fault-response behavior or architecture
  beyond what has been explicitly and publicly released by NASA or the
  relevant agency for open use.

If a future need arises to use a dataset whose status is unclear, the
free/public BIS (Bureau of Industry and Security) guidance channel is
available for informal classification questions — use it before using the
data, not after.

## 4. Publication note

When submitting to venues that ask about export control compliance
(common at AIAA and other aerospace-adjacent venues), this project's clean
answer is: built entirely on open-source software (cFS, Apache 2.0),
public-domain/synthetic data, and open standards (CCSDS) — no real
operational or export-controlled data used at any stage.
